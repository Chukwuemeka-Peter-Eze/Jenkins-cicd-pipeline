# Overview

This repository demonstrates the implementation of a Jenkins-based Continuous Integration (CI) pipeline for a Java Maven application.

The project was built and tested on an AWS EC2 Ubuntu instance and integrates several DevOps tools to automate the software build process.

Core technologies include:

- Jenkins
- Java
- Maven
- Docker
- Sonatype Nexus Repository
- GitHub
- Linux (Ubuntu)
- Groovy

# Jenkinsfile

## Purpose

The `Jenkinsfile` defines the Continuous Integration pipeline.

Rather than configuring jobs manually through the Jenkins web interface, the pipeline is stored as code and version-controlled with the project.

---

## Responsibilities

The pipeline typically performs the following stages:

```
Checkout Source Code
↓

Build Project

↓

Run Maven Package

↓

Build Docker Image

↓

Authenticate to Nexus

↓

Push Docker Image
```

---

## Why It Matters

Using a Jenkinsfile provides:

- Repeatable builds
- Version-controlled automation
- Easier collaboration
- Consistent CI workflows

---

# Dockerfile

## Purpose

Defines how Docker should package the Java application into a container image.

---

## Responsibilities

Typical workflow:

```
Base Image

↓

Copy Application JAR

↓

Set Working Directory

↓

Define Startup Command
```

---

## Why It Matters

A Dockerfile makes application packaging:

- Consistent
- Portable
- Reproducible

---

# pom.xml

## Purpose

The `pom.xml` file is Maven's project configuration file.

It contains:

- Project metadata
- Dependencies
- Plugins
- Build configuration
- Java version
- Artifact information

---

## Why It Matters

Maven reads this file to determine how to build the application.

Without it:

- Dependencies cannot be resolved.
- The application cannot be packaged correctly.
- Plugins cannot execute.

# target/

The `target` directory is automatically generated by Maven.

It contains:

- compiled classes
- packaged JAR files
- build artifacts
- temporary build files

Example:

```
target/

java-maven-app.jar

classes/

generated-sources/

maven-status/
```

---

## Important

This folder should **not** be edited manually.

It is recreated every time Maven performs a build.

# Build Flow

The complete build process follows this sequence:

```
Developer Pushes Code
           │
           ▼
GitHub Repository
           │
           ▼
Jenkins Job
           │
           ▼
Checkout Source Code
           │
           ▼
Maven Build
           │
           ▼

           │
           ▼

           │
           ▼

           ▼
```

# Best Practices Applied

During this project, the following engineering practices were followed:

- Pipeline as Code using `Jenkinsfile`
- Version control with Git and GitHub
- Build automation with Maven
- Containerization using Docker
- Artifact management with Nexus Repository
- Documentation-first approach
- Troubleshooting based on log analysis
- Cloud-based development on AWS EC2

# Conclusion

The repository is organized to separate application code, build configuration, automation scripts, documentation, and supporting assets.

This structure improves readability, maintainability, and collaboration while reflecting common practices used in professional DevOps environments.
